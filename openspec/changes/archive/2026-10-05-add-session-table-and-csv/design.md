# Design

## Context

See proposal.md for motivation. What exists today: `components/ReceiptWorkspace.tsx` holds exactly one receipt in React state, beside its warnings, its edited list, its standing refusals, its line item keys, the measurement and the selected field. `lib/receipt-json.ts` builds the one envelope, `{ receipt, warnings, edited }`, and `RECEIPT_JSON_FILENAME` carries a comment saying slice 6 settles the batch shape. The workspace tells the visitor in so many words that a reload loses the receipt, which this slice makes false.

Two constraints shape the approach. There is still no DOM test environment (`vitest.config.mts` sets `environment: "node"`), so anything that must be unit-tested belongs in a pure module under `lib/`. And the nothing-is-stored rule is about the server: the browser is where results have always lived, and IndexedDB is what the spec named from the start.

## Goals / Non-Goals

**Goals:**

- A table that survives a reload and ends with the tab, with every receipt carrying the warnings and edits it had.
- A CSV builder that is pure, unit-testable in Node, and shared by the single and the batch export so the two shapes cannot drift.
- One column order, stable across exports, so a script written against one file reads the next.
- Reopening a receipt that works on every control already on screen, with no second code path.

**Non-Goals:**

- Batch upload. Receipts arrive one at a time and the five-file cap stays with slice 7.
- Keeping the uploaded image. The app stores no upload, so a reopened receipt has fields and no picture, and the pane says so.
- Deleting or renaming a stored receipt. Nothing in the spec asks for it and the no-deletion habit of this repo argues against adding it unasked.
- The 40-per-session cap. That is slice 7's, and this slice must not quietly enforce a different number.
- Syncing across tabs. The table is keyed to one tab session by design.

## Decisions

**The session key is a random id in `sessionStorage`, and the IndexedDB records carry it.** `sessionStorage` is per tab and dies with the tab, which is exactly the lifetime the spec asks for, while IndexedDB is per origin and outlives it. Holding one database and keying each record by the session id gives the spec's behavior without a database per tab, and a record whose session is gone is simply never listed. The alternative, a database named after the session, leaves an unbounded pile of databases no code ever opens again. A later slice that wants to sweep orphaned records has one index to scan; this slice does not sweep, because deleting a visitor's data unasked is the thing this repo does not do.

**IndexedDB is used directly, with no wrapper library.** The app needs open, put, get and a keyed list, which is one `onupgradeneeded` and four small promise wrappers. `idb` would add a dependency for ergonomics the app uses four times. The wrappers live in `lib/session-store.ts` behind functions named for what they do, so a later swap is contained.

**A stored record is the envelope plus an id, a session and a timestamp.** It holds `receipt`, `warnings` and `edited`, which are the three the download already carries, so a reopened receipt needs no reconstruction and the batch export reads the same shape as the single one. The timestamp orders the list newest first. The id is generated by the browser, never by the model, and never reaches the receipt object, for the same reason the line item row keys do not: it is a fact about this browser, not about the receipt.

**Writes go through one function that the extraction and the edit paths both call.** The workspace already recomputes warnings on every accepted edit, so the record is put again on every edit rather than only on extraction. That makes the stored record true at all times rather than true at scan time, which is what the spec's "a correction after a reopen" scenario asks for. The put is fire-and-forget against the render: a failed write logs and leaves the receipt on screen working, because losing the table is worse than losing the receipt but neither should blank the panel.

**The CSV is built from a column spec, not from string concatenation.** `lib/receipt-csv.ts` holds an array of column definitions, each a name and a reader, which is what makes the stable order a property of one list rather than of the order someone wrote the template. The tax pairs are generated from the widest receipt in the export, so sizing is one `Math.max` over the set rather than a special case for the batch. The single-receipt export is the batch export over a list of one, which is the only way the two shapes cannot drift.

**Column names carry their level as a prefix.** The receipt's own fields keep their property names (`merchant`, `date`, `subtotal`, `total`), the tax pairs read `tax_1_label` and `tax_1_amount`, and the item columns read `item_description`, `item_quantity`, `item_unit_price` and `item_amount`. A reader who sees `amount` alone cannot tell a line from a receipt, which is the mistake the prefix exists to prevent. Snake case throughout, because a spreadsheet header with a space in it is awkward to reference in a formula and the JSON export is where the camel-case property names already live.

**CSV carries no confidence and no source text.** Thirty-odd fields each gaining two siblings would triple the width of a row a visitor opened to see amounts. The JSON export already carries both, and the control says so. This is a decision the spec now states rather than an omission.

**Quoting is minimal and the values are untouched.** A cell is quoted only when it holds a comma, a double quote or a newline, with an inner quote doubled, which is RFC 4180 without the parts nothing here needs. No leading apostrophe to stop a spreadsheet reformatting a date, and no currency symbol: the app's contract is the decimal string it holds, and a file that adds a symbol has changed the value. A receipt whose date a spreadsheet mangles on import is the spreadsheet's choice, and the JSON export is the lossless path.

**The session table is its own component, and the workspace owns the selection.** `components/SessionTable.tsx` renders rows and reports a selection upward, the way `FieldPanel` reports a focused field. The workspace holds which record is open and feeds the panes from it, so the reopen path and the just-extracted path are the same state. Nothing in `FieldPanel`, `lib/field-edit.ts`, `lib/arithmetic.ts` or `lib/highlight-match.ts` changes.

**A reopened receipt has no image, and the pane says so.** The app stores no upload, so there is nothing to show and nothing to measure. The document pane carries one sentence explaining it, the regions for that receipt are absent, and the panel's existing "could not find that text" wording is not reused, because a missing picture is a different fact from a failed match.

## Risks / Trade-offs

- **IndexedDB is unavailable or throws in a private window or with site data blocked.** → Every call is wrapped, a failure logs once and the app runs exactly as it does today with one receipt on screen. The list simply never appears, and the workspace does not claim a table it does not have.
- **A visitor who scans many receipts grows the table without a cap.** → Slice 7 owns the 40-per-session cap, and this slice deliberately enforces no number of its own rather than guessing one that slice 7 then has to change.
- **Sizing tax columns to the widest receipt means one wide receipt widens every row.** → That is the cost of one header per file, which is what a spreadsheet needs. The empty cells are empty, not zero, so nothing reads as a tax of nothing.
- **`navigator.clipboard.writeText` needs a user gesture and a secure context, and can still refuse.** → The copy runs from the press itself, and a refusal says the copy did not happen rather than reporting a success. The download stays the reliable path, which is what the spec's refusal scenario asks for.
- **The table and the live state can disagree if a write fails mid-session.** → The put happens on every accepted edit, so the next successful write repairs it, and the receipt on screen is always the authority for what the visitor is looking at.
- **Still no DOM test environment**, so the table rendering, the row keyboard path and the clipboard rest on the browser check rather than on unit tests. → Same answer the last three slices gave: the CSV builder, the column sizing, the quoting and the record shape are pure modules with tests, and the components stay thin. Adding jsdom and `@testing-library/react` remains the open improvement.
